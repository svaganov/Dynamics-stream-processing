# План: полная контейнеризация (панель + воркеры в Docker)

## Цель и критерий готовности

На чистой машине (Windows + Docker Desktop или Linux + Docker Engine)
**ничего, кроме Docker, не установлено**. Оператор выполняет одну команду
`docker compose up -d` — и через несколько минут панель доступна на
`http://<хост>:8770`, станции стартуют, подслушка A/B звучит. Наружу
проброшены только порт панели и том данных.

## Архитектура

```
┌─ хост: только Docker ──────────────────────────────────────────┐
│  контейнер ПАНЕЛЬ (audio-panel)      контейнеры-ВОРКЕРЫ        │
│  · Python 3.12 + Flask + docker SDK  (audio-worker:2.4.2,      │
│  · FFmpeg (подслушка A/B, запасной    по одному на станцию,    │
│    движок)                            Liquidsoap)              │
│  · UI + API + генератор .liq        · создаются панелью        │
│  · entrypoint: автосборка образа      динамически              │
│    воркера, если его нет            · telnet :1234             │
│  общее: сеть audiopanel_net · том panel-data                   │
│  наружу: только порт 8770                                      │
└────────────────────────────────────────────────────────────────┘
```

## Ключевые проектные решения

1. **Общий named volume `panel-data` вместо bind-путей.** Панель пишет
   `streams.json` и `runtime/<id>.liq` в `/data`; воркеры создаются с маунтом
   того же тома (read-only) и читают скрипт оттуда. Демон сам разрешает том —
   полностью уходит кухня `WORKER_BIND_ROOT` и хостовых путей, одинаково
   на Windows и Linux.
2. **Общая docker-сеть `audiopanel_net`.** Воркеры — в той же сети, панель
   достаёт telnet :1234 по имени контейнера. Публиковать telnet-порты на
   хост больше не нужно вообще — чище изоляция, меньше сетевых швов.
3. **FFmpeg внутри образа панели** (Debian-сборка): подслушка A/B и запасной
   FFmpeg-движок работают без хостового ffmpeg. `libfdk_aac` там нет →
   нативный `aac` (вариант в модели уже есть); Liquidsoap-воркеров это не
   касается, в их образе FDK.
4. **Автосборка образа воркера при старте панели.** Контекст (один
   `worker/Dockerfile`) зашит в образ панели; entrypoint через `docker.sock`
   проверяет наличие `audio-worker:2.4.2` и собирает при отсутствии
   (контекст уходит демону tar-потоком — хостовые пути не нужны).
   Отключается `WORKER_AUTO_BUILD=0`.
5. **`docker.sock` — единственная точка соприкосновения с хостом.** Без него
   панель не создаст воркеров (альтернатива DinD — тяжелее и медленнее).
   Осознанная оговорка: sock = root на хосте; документируем. Изоляция софта
   и ФС при этом полная.
6. **Хостовый режим (run.bat / python app.py) сохраняется** — автодетект
   `/.dockerenv` уже есть в коде. Демо-контур на 9101 не ломаем.

## Этапы

| Этап | Содержание | Проверка |
|---|---|---|
| A. Образ панели | +ffmpeg в Dockerfile, `COPY worker/ /worker_build/`, entrypoint с автосборкой воркера | юнит-тесты с моком docker API (есть/нет образа, флаг выкл) |
| B. Сеть и том | `DockerWorkerManager`: воркер в `audiopanel_net` + маунт named volume, telnet по имени контейнера; `extra_hosts: host-gateway` для Icecast/источника на хосте; хостовый режим — как сейчас | новый песочный тест: панель-в-контейнере поднимает воркера, telnet по имени, поток идёт |
| C. Compose и документы | compose v2 (network, volume, sock), убрать сервис-заглушку worker; инструкция «чистая машина = Docker + одна команда»; сноска про docker.sock; (опция) профиль `icecast` для автономного стенда | `docker compose config` |
| D. Проверки | чистовой прогон с удалёнными образами одной командой; регрессия хостового режима (юнит 55/55, песочница 8/8, демо на 9101); миграция существующего `streams.json` в том | все зелёные |

## Риски

- Первый запуск тянет образы (python:3.12-slim, savonet/liquidsoap) —
  сотни МБ, нужен интернет.
- Живой Linux здесь не проверить — только синтаксис compose; первая
  реальная проверка на вашей Linux-машине.
- SELinux-хосты (RHEL/Fedora) могут требовать `:z` на маунте sock —
  отразим в инструкции.
- Registry (GHCR) для образов — следующий шаг после этого: уберёт
  автосборку и ускорит первый запуск.
